# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `bun run test` — run the full suite in two lanes: 4 parallel workers over every file except `*.serial.test.ts`, then the `*.serial.test.ts` files serially; the full-suite gate uses this command
- `bun test` — run every file serially
- `bun test tests/scanner.test.ts` — run one test file
- `bun test -t "pattern"` — run tests matching a name
- `bun run typecheck` — `tsc --noEmit`, then `tsc --noEmit -p dashboard`
- `cd dashboard && bun run build` — rebuild the dashboard page; vite empties `dashboard/dist/` first and drops its `.crank-version` stamp, so `crank-mem dashboard` refuses as not built until `crank-mem setup` (or any `crank-mem upgrade`) restamps it
- `bun scripts/pack-release.ts --out <dir> --dist <built dashboard dist dir>` — pack the release tarball, its `.sha256` and `release.json` (the `v*` tag workflow `.github/workflows/release.yml` runs it; `docs/releasing.md` holds the steps); `install.sh` is the `curl … | sh` installer that downloads a release into `~/.crank/versions/` and runs its `crank-mem self-install`
- `bun scripts/recall-eval.ts [--root <dir>] [--set <file>]` — replay each digest's request, or with `--set` each question of a labelled set (one `{"id", "query"}` JSON object per line, the id naming the one relevant observation; this repo's set is `.crank/eval/recall-set.jsonl`, kept out of git), against the project's store; print `mode hybrid` or `mode keyword` first, then recall@5, recall@10 and mean reciprocal rank (`mrr`) with and without the graph list; a dev script that writes nothing
- `bun run release <patch|minor|major|X.Y.Z>` — `scripts/release.ts`: run the gates, bump `package.json` → `version`, commit, tag `v<version>` and push `main` with the tag, which runs the release workflow (`docs/releasing.md`)
- `crank-mem upgrade --all` — repair every project in `~/.crank/projects.json`; `crank-mem self-install` and `crank-mem self-uninstall` put an installed copy in use and remove it, `crank-mem self-update` and `crank-mem rollback` move it to a newer or the previous version, and all four refuse to run from a clone
- `bun run format` / `bun run format:check` — oxfmt (pinned exact in `package.json`). `.oxfmtrc.json` leaves out `tests/fixtures/`, whose bytes the `.outline`/`.headers` goldens record, and all markdown, whose ADRs quote probe output verbatim and whose README shows JSONL one record per line, and `.impeccable/`, which the Impeccable design tool writes in its own style
- `bun run lint:health` — knip (dead code, `knip.json`) then fallow (cognitive complexity over 15, `.fallowrc.json`); the release `check` job and `scripts/release.ts` run it. `bunx fallow health --complexity --no-cache -q <file>` checks one file (fallow is a devDependency, not on `PATH`); it takes a single path, and a second one exits 2 (`unexpected argument`)

`bun test` needs `crank-mem setup` (or `bun src/cli/main.ts setup`) run once on the machine: `tests/digest-job.test.ts`, `tests/embedder.test.ts`, `tests/setup.test.ts`, `tests/cli-commands.test.ts`, `tests/dashboard.test.ts`, `tests/release.test.ts`, `tests/installed-copy.test.ts` and `tests/self-update.test.ts` read the real model it downloads into `~/.crank/models`, and `tests/dashboard-page.test.ts` imports React from the `dashboard/node_modules` it installs.

There is no build step except the dashboard, which `crank-mem setup` builds into `dashboard/dist/` (`upgrade` rebuilds it when the stamp is not the clone's version). `bin/crank-mem` is a shell launcher that runs `src/cli/main.ts` directly under bun (or node >= 23.6, which also executes TypeScript natively). Hooks under `src/hooks/` import only `node:` modules, and `tests/hooks-imports.test.ts` enforces it; `src/daemon/` and `src/cli/code-symbols.ts` may carry packages, loaded by dynamic `import()` so every other command works without them. `package.json` pins three packages exact: `@huggingface/transformers` for the embedder, and `web-tree-sitter` and `@vscode/tree-sitter-wasm` for `outline` and `unfold`; it also pins the devDependencies `knip` and `fallow` exact.

## What this is

Project memory for coding agents (Claude Code + Codex): a token-annotated file anatomy index plus a `cerebrum.md`, injected at session start and silently re-indexed on writes. With `crank-mem digest on`, finished Claude Code sessions, and live ones every 2 hours, are digested automatically into `.crank/memory.db` (SQLite with FTS5 plus local embeddings); after a digest, consolidation checks the digests' proposals and stale flags against the code and keeps `cerebrum.md`, which agents no longer write. Agents recall the store through `crank-mem search`, `timeline` and `get`, session-start sections and per-file history. Installed into a target project as `.crank/` (index, anatomy.md, cerebrum.md, memory.db, config.json, vendored hooks, backups, including the daily `backups/memory/` snapshots of memory.db); per-user state (digest spool, daemon heartbeat, stop state, models, the dashboard's token, pid and version in `dashboard.json`, the project registry in `projects.json`, the installed copies in `versions/`, the `current` link to the one in use, `tool.lock`, held while an install or update runs, and the release check's settings and last result in `update.json`, and in `untouched.json` the git repos agents read or wrote that have no install, which `stats` and the Health view list) lives under `~/.crank` (`$CRANK_HOME`). `skills/crank-mem-audit/` is the bundled audit skill; `tests/skill.test.ts` holds its `SKILL.md` frontmatter to the fields the skills installer reads.

## Architecture

Three entry surfaces share one core:

- **CLI** (`src/cli/`) — `main.ts` dispatches to per-command modules (`init`, `scan`, `digest`, `search`, `timeline`, `get`, `outline`, `unfold`, `restore-memory`, `setup`, `stats`, `dashboard`, `upgrade` (with `--all`, every registered project), `uninstall`, `self-install`, `self-uninstall`, `self-update`, `rollback`, plus the internal `daemon` and `job`) via dynamic imports. `main.ts` checks a command's flags against its entry in `src/cli/commands.ts` → `COMMANDS` before loading it: a flag without an entry fails as `unknown flag`, and a command without one prints usage and exits 1. `search`, `timeline` and `get` live in `src/cli/recall.ts`. `src/cli/settings.ts` merges hook entries into the agents' settings files and removes them, and holds `SUBAGENT_MATCHER`; `src/cli/backups.ts` copies every file `init` or `upgrade` is about to modify; `src/cli/codex-trust.ts` writes Codex `trusted_hash` entries (ADR 0002); `src/cli/codex-sessions.ts` tells `stats` whether the injection reached Codex threads (ADR 0006). `src/cli/code.ts` holds `outline` and `unfold`, and `src/cli/code-symbols.ts` holds the tree-sitter reader they share, with its per-language rule tables in `src/cli/code-families-compiled.ts` and `src/cli/code-families-scripting.ts`. `src/cli/install.ts` holds the ordered install items behind `applyInstall`, `repairInstall` and `removeInstall`, with the Claude and Codex wiring items in `src/cli/install-agents.ts`, the git-ignore items in `src/cli/install-gitignore.ts`, and their shared report and file helpers in `src/cli/install-support.ts`. `src/cli/dashboard.ts` is the foreground `dashboard` command (flags, the token file, the port-taken check, signals); `src/cli/dashboard-server.ts` → `serveDashboard` applies every guard and serves the static `dashboard/dist/` build and the `/api` routes over `node:http`, reading each store through `readStore(root, fn)`; `src/cli/usage-metrics.ts` is the pure aggregator of usage lines behind `/api/projects/<id>/usage` and of the store's per-day upkeep behind `/api/projects/<id>/activity`; `src/cli/stats.ts` → `captureSummary` builds the capture summary and its status (`src/hooks/lib/wire.ts` → `projectStatus`), which `/api/projects/<id>/health` answers and `stats` prints. `src/cli/self-install.ts` and `src/cli/self-uninstall.ts` put an installed copy in use and remove it; `src/cli/self-update.ts` holds `self-update` and `rollback`, which make a newer or the previous version `current` and repair every project from it, refusing to go back to a version older than a registered store's schema; `src/cli/tool-install.ts` holds their shared steps (the per-user `tool.lock`, the copy's packages and dashboard check, the `current` link and the bin link), and `src/cli/shell-rc.ts` adds and removes the marked PATH block in the shell rc file. `src/cli/updates.ts` holds the release check: `update.json` (the `checkDaily` and `auto` settings and the last check's result), `checkNow` (fetches the latest release's `release.json`), `checkDue` (an installed copy with daily checks on and no check in 24 h), `laggingProjects`, and the update notice human-run commands print; `/api/updates` answers it to the dashboard, whose server also checks when due at start and on a timer. `scripts/pack-release.ts` packs a release and `install.sh` installs one. The page itself is a separate Vite + React package in `dashboard/`; `dashboard/src/views/updates.tsx` is its display-only Updates section on the Health view. Runs from the clone or an installed copy (`toolRoot()`).
- **Hooks** (`src/hooks/session-start.ts`, `src/hooks/post-write.ts`, `src/hooks/post-read.ts`, `src/hooks/stop.ts`, `src/hooks/session-end.ts`, `src/hooks/subagent-start.ts`) — invoked by the agents with a JSON payload on stdin. `init` vendors a recursive copy of `src/hooks/` (including `lib/`) into `<project>/.crank/hooks/` (`src/cli/vendor.ts`), so hooks run self-contained inside each target project while the CLI imports the same `lib/` from the clone or installed copy it runs from. Consequence: everything under `src/hooks/` must work from either location and import nothing outside `src/hooks/`. `stop.ts` and `post-write.ts` emit nothing model-visible (ADRs 0004 and 0010). Claude subagents never see SessionStart, so `subagent-start.ts` emits `injection.ts` → `subagentInjection`'s text to the agent types in `SUBAGENT_MATCHER`: a 2 KB cerebrum excerpt, the code pointer and the recall pointer (ADR 0007). Stop and `session-end.ts` write the session's digest spool entry; `post-read.ts` adds a file's stored history when Claude reads it with Read or Bash (ADR 0009).
- **Daemon** (`src/daemon/`) — never vendored; runs from the clone or an installed copy: `daemon.ts` (one per user, sweep loop starting one `crank-mem job` at a time; its first sweep starts the release check when due, and with `auto` on in `update.json` an installed copy runs `self-update`, or `upgrade --all` for lagging projects, as its one child between digest jobs), `digest-job.ts` (one-shot digest of a spool entry: a share into each other owning project's `memory.db` first, then the entry project's digest, then per-store upkeep), `digest-route.ts` (splits a digest's observations, proposals and stale flags across the stores that own their files), `gateway.ts` (`claude -p` on the user's own login, the only spawn of `claude` — ADR 0008), `digest-prompt.ts`, `consolidate.ts` (consolidation after a digest: a `claude -p` run with read-only tools over the project reviews proposals, stale flags and bullets whose cited files changed, then edits `cerebrum.md` — ADR 0011), `cerebrum-edit.ts` (pure bullet numbering and edit application), `redact.ts` (always-on secret redaction), `transcript.ts` (transcript reader and distiller) and `embedder.ts` (local embeddings).

The shared core is `src/hooks/lib/`: `owner.ts` (`ownerOf`, the one ownership walk every project lookup goes through — the nearest installed `.crank/config.json`, a linked worktree's main checkout, or an unowned git repo — plus `projectName`; it spawns no git), `untouched.ts` (`untouched.json`: post-read and post-write record each unowned repo with its session, once per run under `untouched.lock`), `scanner.ts` (index refresh with time budget), `indexable.ts` (which relative paths the index may hold: binary, lockfile, test-path and name gates), `activity.ts` (git listing and churn-driven index activity), `store.ts` (anatomy-index.json load/save + anatomy.md render), `imports.ts` (each indexed file's repo-file imports and, for C#, its declared and used namespaces, resolved by regex at index time), `related-files.ts` (a query's starting files and their one-hop import neighbours over an `AnatomyIndex`), `injection.ts` (both start injections: `sessionStartInjection` for SessionStart and `crank-mem stats`, `subagentInjection` for SubagentStart; each gathers its sources and returns the text and its usage event), `bullets.ts` (markdown bullet grouping shared by the cerebrum excerpt and consolidation — whole bullets, headings as hard boundaries), `cerebrum-files.ts` (memory file names, cerebrum's size limits, the `backups/cerebrum/` copies and audit-backup detection), `drift.ts` (one-line warning when the vendored hooks lag the running crank-mem), `symbols.ts` / `tokens.ts` / `describe.ts` (per-file analysis), `config.ts` (.crank/config.json + always-on sensitive-file filter), `lock.ts` (cross-process lock around index writes), `hook-io.ts` (stdin parsing, project-root discovery, `additionalContext` emission, `repoRelative`, `ownedPath` and `ownedPaths`), `memory.ts` (owns the project root → `memory.db` mapping and every open of a project's store over `node:sqlite`, loaded through `process.getBuiltinModule`: `readStore` and `readStoreSync` call a reader over the root's store and close it, returning the status with the value, `storeStatus` and `storeVersion` answer without a handle, `openStoreForWrite` returns the writer, and file-keyed `openMemory`, which they wrap, stays exported for opens of a bare file; wires the `memory-read.ts`, `memory-search.ts` and `memory-write.ts` functions into its `Memory` object; also `restoreMemory` and `migrateStore`, the migration `upgrade` and `restore-memory` share), `memory-schema.ts` (memory.db's schema steps, `SCHEMA_VERSION` and `migrate`), `memory-read.ts` (the store's read queries), `memory-search.ts` (the store's hybrid `search`: FTS, vector and import-graph results fused by reciprocal rank), `memory-write.ts` (the store's writes: digests, rejections, vectors, consolidation records and the daily `maintain`), `store-upkeep.ts` (memory.db's snapshot folder and names, the daily pass — snapshot every 24 h, keep 7 daily snapshots, delete rows stale over 90 days — the pre-migration snapshot and the save before a restore), `registry.ts` (the per-user project list in `projects.json` that `init`, `upgrade` and the session-start hook add to and `uninstall` removes from), `spool.ts` (per-user digest spool, daemon start, `digestGate`), `user-state.ts` (`<crank home>`, stop state), `shell-reads.ts` (files a Bash command reads), `apply-patch.ts` (Codex patch-text parsing), `debug.ts` (opt-in per-run JSONL trace to `.crank/debug.log`, off by default), `usage.ts` (`recordUsage`, the always-on usage line contract appended to `usage.jsonl` beside `memory.db` and rotated to `usage.1.jsonl` at 4 MiB), `wire.ts` (the server↔dashboard wire vocabulary: observation, proposal, stale, consolidation and usage shapes, their constants and guards, and `projectStatus`, the status rule `captureSummary` applies, whose result `/health` answers and `stats` prints, `StoreStatus` and `STORE_TEXT`, the one table of each store status's note, stats state and fix; imports nothing, so the dashboard page imports it).

### Invariants

- **Hooks are advisory-only: every path exits 0.** Never let a hook throw, block, or emit errors that could break an agent session. A corrupt or missing index degrades to `emptyIndex()` and reconverges on the next scan.
- All index writes happen under `withLock`; hooks operate under hard time budgets (refresh budget, lock-wait budget) and report staleness in the injection rather than blocking.
- The sensitive-file filter in `config.ts` is not configurable — never index secrets.
- Model-visible output goes only through `hookSpecificOutput.additionalContext` on stdout; stderr is human/debug-only (see ADR 0001).
- Debug logging is subject to the same advisory-only contract: `debug.ts` never throws, never writes to stdout, and never records a sensitive path.

### ADRs record probe-verified agent behavior

`docs/adr/` documents live-probed facts about Claude Code and Codex (which hook channels reach the model, Codex's trust-hash formula, Codex tool shapes — notably: Codex has no Read tool, and writes arrive as `apply_patch` patch text). Design decisions rest on these probes; don't change behavior they cover without re-probing (method is in each ADR), and record new probe findings as ADRs.

## Testing conventions

Tests are black-box: hooks and CLI commands are executed as real child processes with agent-like stdin payloads via `runHook` and `runCli` in `tests/helpers.ts`, with `fakeClaude` standing in for the `claude` binary and `startDaemon` running the real daemon under a temp `CRANK_HOME` (no test runs the real `claude`), against temp projects built by `makeCrankProject`. Agent payload fixtures live in `tests/fixtures/payloads.ts`. Prefer this style over importing hook internals — assertions should hold against exit status, stdout JSON, and on-disk `.crank/` state.

`bun test` runs the test process in UTC with `TZ` unset, while `runCli` and `runHook` children run in the system zone (a test that spawns its own child builds its env with `tests/helpers.ts` → `childEnv`, which drops the `TZ` a zone test left at `"UTC"`), so an in-process local-date assertion passes against UTC getters too. Pin local dates in zones on both sides of UTC (`tests/helpers.ts` → `ZONES`): an in-process test may set `process.env.TZ` per zone and must restore it to `"UTC"`, never `delete` it, which falls back to the machine zone; a CLI child with `TZ` in its env still works.

A `tests/dashboard-page.test.ts` test that deep-links an `item` also sets `project` in the URL: without it `dashboard/src/App.tsx` → `App`'s projects poll picks the first project and resets `item` to null.

An installed-copy test puts `tests/helpers.ts` → `fakeTool("bun", "runtime")` on `PATH`; it records every `bun` call the launcher makes (it runs non-`install` calls through the real runtime), so an oracle meaning "no package install ran" filters `calls()` for `install`.

The `spawnSync` timeout in `tests/helpers.ts` → `runCli` kills only the CLI child; a grandchild that hangs, such as `fakeClaude` with `auth: "hang"`, keeps running at ppid 1. After a RED run that hit the timeout, find leftover fake `claude` processes with `ps` and kill them.

Run the full suite as `caffeinate -i bun run test`; on battery a Mac sleeps mid-run. `Expected: 0, Received: -1` near 5 s is a per-test timeout, not a crash; `docs/testing-load.md` holds the baseline. Bun prints per-test durations only to a TTY, so a piped or `tee`d run shows none; add `--reporter=junit --reporter-outfile <file>` to get them.

The preload (`tests/preload.ts`) gives each test process temp `CRANK_HOME`, `CODEX_HOME` and `TMPDIR` under one root it removes in `afterAll`: each file is its own process under `--parallel`, while plain `bun test` and the serial lane share one process, so their files share the root and any per-process memo (`initedCopy`, `sharedDashboardDir`).

To probe an fs failure path (such as `src/hooks/lib/spool.ts` → `settleEntry`'s non-`EEXIST` link fallback), run the probe under node: assigning `fs.linkSync` on the default `node:fs` import and calling `syncBuiltinESMExports()` reaches a module's `import * as fs` namespace under node 26 (the call threw the mock's `EPERM`) but not under bun 1.4 (it threw the real `ENOENT`).

Under bun 1.4, `fs.statSync(p, { throwIfNoEntry: false })` still throws `ENOTDIR` when a component of `p` is a regular file (node returns `undefined`), so a stat that must not throw catches per call, as `src/hooks/lib/hook-io.ts` → `isProjectFile` does; `tests/imports.test.ts` → "a specifier through a regular file costs only that specifier" pins it.

Under bun 1.4, a `readOnly: true` open of a closed WAL store with no `-shm` throws `unable to open database file` (node opens it), so every read of a store or snapshot goes through `src/hooks/lib/memory.ts` → `openForRead` (read-write open, `query_only`, null for a missing file); `tests/helpers.ts` → `plantMemory("newer")` plants a WAL store so `tests/self-update.test.ts` and `tests/snapshots.test.ts` catch a regression.

To make another project's store fail in a test, chmod its `memory.db`, never its `.crank/`: `src/hooks/lib/owner.ts` → `isInstalled` is an `existsSync` of `.crank/config.json`, so `.crank` at `0o000` makes `ownerOf` report the project's files unowned and the test exercises a different path. A `0o000` store opens as `unreadable` (`tests/cross-repo.test.ts` → "post-read stays silent when another project's store cannot be read"). A `0o444` store opens `"open"`, and its first write throws `ERR_SQLITE_ERROR` "attempt to write a readonly database". SQLite creates `-wal` and `-shm` at the store's mode, so restore all three files or the next open fails `database is locked` (`tests/cross-repo.test.ts` → "a share written before the entry write fails stays, and the retry skips it").

A race test that spawns hooks through `runHook`'s argv races only about 1 time in 10 when the hook's read-to-write window is short: bun start-up spreads the children 5–13 ms apart. Release writer processes at one start time instead, as `tests/usage.test.ts` → "concurrent writers at the 4 MiB mark rotate once and keep every line" does with `tests/fixtures/usage-writer.ts`.
